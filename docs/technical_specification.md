# Техническое задание

## 1. Общие сведения

**Наименование системы:** `ars_fracta`.

**Назначение:** настольное приложение для интерактивной визуализации фракталов и процедурных трехмерных сцен с использованием OpenGL и метода ray marching.

**Целевая платформа:** Windows, а также среды с поддержкой C++17, CMake и OpenGL 3.3 Core.

**Тип продукта:** локальное графическое приложение без обязательного сетевого взаимодействия после установки зависимостей.

## 2. Цели разработки

Программа должна обеспечивать:

- визуализацию математических фракталов и процедурных сцен в реальном времени;
- изменение параметров сцены через графический интерфейс;
- управление виртуальной камерой мышью и клавиатурой;
- сохранение и загрузку конфигураций и пресетов;
- создание PNG-скриншотов;
- построение внешней поверхности губки Менгера и экспорт в OBJ и binary STL;
- выполнение трудоемких CPU-операций в фоновом потоке без блокировки интерфейса;
- автоматическую проверку корректности параметров и наличие модульных тестов core-компонентов.

## 3. Функциональные требования

### 3.1. Поддерживаемые режимы визуализации

Система должна предоставлять следующие режимы:

| Режим | Описание |
|---|---|
| Mandelbrot 2D | Визуализация множества Мандельброта на плоскости комплексных чисел |
| Mandelbulb 3D | Трехмерный фрактал Mandelbulb с distance estimator |
| Menger Sponge | Визуализация губки Менгера |
| Julia 3D | Трехмерное множество Жюлиа с настраиваемыми комплексными параметрами |
| Terrain 3D | Процедурный ландшафт на основе fBm-шума и фрактальных форм |
| Coast 3D | Процедурное морское побережье, связанное с границей множества Мандельброта |

Для каждого режима приложение должно выбирать соответствующий алгоритм в GLSL-фрагментном шейдере. Параметры, не применимые к выбранному режиму, должны игнорироваться и не должны приводить к сбою программы.

### 3.2. Настройка сцены

Через панель управления пользователь должен иметь возможность изменять применимые параметры:

- количество итераций;
- bailout и степень фрактала;
- параметры множества Жюлиа;
- детализацию;
- масштаб и режим окрашивания;
- масштаб цвета и сдвиг оттенка;
- параметры ландшафта: амплитуду, частоту, плотность облаков и деревьев;
- время суток и плотность тумана;
- координаты центра побережья;
- автоматическое вращение объекта, если оно разрешено текущим режимом;
- разрешение рендера.

При изменении параметров изображение должно обновляться без перезапуска приложения. Значения должны проходить валидацию и ограничиваться допустимыми диапазонами.

### 3.3. Управление камерой

В области просмотра должны поддерживаться:

- левая кнопка мыши и перемещение: вращение камеры;
- правая кнопка мыши и перемещение: панорамирование;
- колесо мыши: приближение и отдаление;
- `W/A/S/D`: перемещение камеры по горизонтали;
- `Q/E`: перемещение вниз/вверх;
- `ESC`: завершение работы.

Для Mandelbrot 2D колесо мыши должно изменять масштаб плоскости, а не расстояние трехмерной камеры. Для Terrain 3D и Coast 3D должны применяться начальные положения камеры, обеспечивающие видимость рельефа.

### 3.4. Графический интерфейс

GUI на Dear ImGui должен содержать:

- область просмотра результата;
- выбор типа фрактала;
- панели параметров геометрии, цвета, ландшафта и атмосферы;
- управление разрешением;
- список доступных пресетов;
- сохранение пользовательского пресета;
- раздел экспорта губки Менгера;
- строку состояния с FPS и последним сообщением журнала.

Во время фонового экспорта интерфейс не должен зависать. Пользователь должен видеть состояние операции и иметь возможность инициировать отмену построения.

### 3.5. Пресеты и конфигурация

Приложение должно поддерживать JSON-файлы.

**Конфигурация приложения** должна хранить:

- ширину и высоту окна;
- текущий тип фрактала;
- параметры выбранного фрактала.

**Пресет** должен хранить параметры фрактала и применяться через GUI или в режиме создания скриншота.

В поставке должны быть предусмотрены пресеты для всех шести режимов. Пользователь должен иметь возможность сохранить текущие параметры в `assets/presets/custom.json`.

При отсутствии или некорректности конфигурации приложение должно запускаться с параметрами по умолчанию. Загруженные параметры должны быть провалидированы до передачи в рендерер.

### 3.6. Скриншоты

Должен поддерживаться командный режим:

```text
ars_fracta --screenshot <output.png> [preset.json]
```

В этом режиме программа должна:

1. загрузить конфигурацию по умолчанию;
2. при наличии применить указанный JSON-пресет;
3. создать OpenGL-контекст;
4. выполнить отрисовку одного кадра в полном разрешении;
5. сохранить результат в PNG по указанному пути;
6. завершить работу с кодом возврата `0` при успехе.

При ошибке аргументов, загрузки пресета, рендера или сохранения PNG программа должна вывести сообщение в консоль и вернуть ненулевой код.

### 3.7. Экспорт губки Менгера

В GUI должен быть доступен экспорт внешней поверхности губки Менгера.

Требования:

- глубина генерации: целое значение от `0` до `4`;
- генерация mesh выполняется в worker-потоке;
- операция поддерживает кооперативную отмену во время построения;
- после построения создаются `menger_sponge.obj` и `menger_sponge.stl`;
- OBJ должен содержать независимые треугольники и индексы, начинающиеся с 1;
- STL должен быть binary STL в little-endian формате;
- перед записью проверяются непустой mesh, корректность числа вершин, конечность координат и отсутствие вырожденных треугольников;
- ошибки генерации и записи должны отображаться пользователю и журналироваться.

Финальная запись уже построенных файлов может завершаться после отмены генерации.

## 4. Нефункциональные требования

### 4.1. Производительность

- Рендеринг должен выполняться на GPU средствами OpenGL 3.3 Core.
- При движении камеры допускается адаптивное снижение разрешения для сохранения интерактивности.
- После прекращения движения качество должно возвращаться к выбранному разрешению.
- CPU-операции генерации mesh не должны блокировать основной цикл GUI.

### 4.2. Надежность

- Ошибки создания окна, OpenGL-контекста, загрузки шейдеров, конфигурации и файлов должны обрабатываться явно.
- Worker-поток не должен обращаться к OpenGL или ImGui.
- Исключения фоновых задач должны передаваться в поток, ожидающий результат.
- Отмена задания не должна приводить к повреждению состояния приложения.

### 4.3. Совместимость

Минимальные требования среды сборки и запуска:

- CMake версии 3.21 или выше;
- компилятор с поддержкой C++17;
- OpenGL 3.3 Core или выше;
- Python для генерации GLAD;
- доступ к сети при первой конфигурации CMake, если зависимости отсутствуют локально.

### 4.4. Локализация

Приложение должно корректно отображать русскоязычные сообщения и поддерживать UTF-8 в консольном выводе на Windows. Для отображения кириллицы в GUI должен использоваться доступный системный шрифт с поддержкой кириллицы.

## 5. Архитектура и состав компонентов

Система должна быть разделена на следующие подсистемы:

- `core/math`: комплексные числа и векторы;
- `core/fractal`: типы фракталов, параметры, валидация и генерация mesh;
- `core/async`: worker-задачи, ожидание и отмена;
- `core/export`: экспорт OBJ и binary STL;
- `render`: окно, OpenGL-контекст, камера, шейдеры и renderer;
- `gui`: главное окно, панель управления и viewport;
- `utils`: JSON-конфигурация, PNG-запись и журналирование;
- `assets/shaders`: vertex- и fragment-шейдеры;
- `assets/presets`: JSON-пресеты;
- `tests`: тесты CPU/core-части.

Рендерер должен передавать параметры фрактала в GLSL через uniform-переменные. GPU-реализации Terrain 3D и Coast 3D допускается не дублировать в CPU-классах.

## 6. Командная строка

Поддерживаемые варианты запуска:

```text
ars_fracta
ars_fracta <config.json>
ars_fracta --screenshot <output.png> [preset.json]
```

При обычном запуске конфигурация должна сохраняться при корректном завершении приложения. Пути к конфигурации, пресетам и выходным файлам должны поддерживать относительные и абсолютные значения, разрешаемые текущей рабочей директорией.

## 7. Сборка и тестирование

Основные опции CMake:

| Опция | Значение по умолчанию | Назначение |
|---|---:|---|
| `ARS_FRACTA_BUILD_GUI` | `ON` | Сборка GUI и OpenGL-приложения |
| `ARS_FRACTA_BUILD_TESTS` | `ON` | Сборка тестов core |
| `ARS_FRACTA_WARNINGS_AS_ERRORS` | `OFF` | Считать предупреждения ошибками |
| `ARS_FRACTA_ENABLE_COVERAGE` | `OFF` | Инструментация покрытия для GCC/MinGW |

Сборка:

```text
cmake -S . -B build
cmake --build build --config Release
```

Тестирование:

```text
ctest --test-dir build -C Release --output-on-failure
```

Тестовый набор должен проверять математику, CPU-реализации фракталов, валидацию параметров, асинхронные задания с отменой, передачу исключений, JSON round-trip и экспорт OBJ/STL.

## 8. Критерии приемки

Система считается принятой, если выполнены все условия:

1. Проект конфигурируется и собирается указанными CMake-командами.
2. После запуска отображается окно с интерактивным фрактальным изображением и GUI.
3. Все шесть режимов выбираются из интерфейса и отображаются без аварийного завершения.
4. Изменение параметров и управление камерой изменяют изображение в соответствии с назначением.
5. Пресеты загружаются, валидируются и применяются; пользовательский пресет сохраняется.
6. Команда `--screenshot` создает PNG заданного размера и возвращает успешный код.
7. Экспорт губки Менгера создает корректные OBJ и binary STL для глубин `0..4`.
8. Отмена генерации mesh не блокирует и не завершает аварийно GUI.
9. Конфигурация сохраняется при выходе из интерактивного режима.
10. Все автоматические тесты проходят без ошибок.

## 9. Ограничения и допущения

- Производительность зависит от GPU, разрешения, количества итераций и сложности ray marching.
- Режим скриншота использует OpenGL-контекст и не является полностью headless-режимом.
- Terrain 3D и Coast 3D реализуются преимущественно в GLSL и не обязаны иметь CPU-реализацию.
- Глубина экспорта губки ограничена значением `4` для контроля времени выполнения и потребления памяти.
- Отмена применяется к построению mesh; запись уже сформированных файлов может не прерываться.
- Пути по умолчанию разрешаются относительно текущей рабочей директории процесса.
